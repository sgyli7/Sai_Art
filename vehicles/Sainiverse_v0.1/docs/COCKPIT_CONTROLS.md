# Sainiverse_v0.1 physical cockpit controls

All source frames use metres and radians, +X forward, +Y left, +Z up. Visual assets,
physical collision proxies and measured reports are separate. There are 18 actual
moving controls; keyboard and mouse request handle motion using capped PD forces.
The resulting **joint coordinate** supplies the vehicle command. A textured dial
is a display, not a hidden input surface.

| Station | Physical control | Keyboard equivalent | Vehicle function / display |
|---|---|---|---|
| Driver | Continuous three-spoke wheel, ±0.65 rad | A / D | Signed curvature ±0.012 m⁻¹; articulation/yaw rate shown |
| Centre | Speed / reverse lever, ±0.50 rad | W / S | Forward 12 m/s or high range 27.777778 m/s; reverse 5 m/s; actual speed shown |
| Centre | Brake lever, 0–0.50 rad | Space | Progressively reduces speed request to zero |
| Centre | Two-position range selector | Shift while held, or click latched selector | LOW / HIGH state display |
| Centre | Latched PARK / STOP pushbutton | B | Zero-speed hold request, second press releases; not a certified emergency brake |
| Engineer, +Y | Eight-position crane selector | N | Select crane, numbered in system display |

Mouse: click buttons/selectors; drag handles. Camera, theme, free-observer and
capture shortcuts remain application functions, rather than fictional machinery.
The centre panel reports actual range, parking, work mode, door request and lift
position. Its door indication is the commanded state, not a certified latch sensor.
No oil pressure, coolant temperature or electrical readings are fabricated.

## Runtime operation panel

The old shortcut wall is replaced by an accordion panel. Its outer frame contracts
to the header and two live status rows when folded. With the panel open, each task
group remains compact until selected; only one group opens at a time, and a vertical
scroll limit keeps every control reachable at 720p. UI pointer events are consumed
before cockpit picking and camera orbit, so a slider or crane hold button cannot
also manipulate the 3D scene.

The panel exposes drive/reverse, steering, brake, range and park; selection and
finite motion commands for all eight cranes; hook/release; selected/all lift
commands; receiver slew/fold; doors and work/stow; view, theme, capture and quit.
Crane motion buttons are momentary: button-down commands a direction, button-up
or leaving the button zeros that axis. UI commands drive the same physical cockpit
joint targets as keyboard controls, and mechanism controllers continue to read the
measured joint coordinates rather than a parallel hidden command path.

## Future robot manipulation

`source/cockpit_controls.json` contains each named control's axis, limits, mass,
inertia, effort cap, collision shapes, grasp point and approach normal. Controls
use collision layer 128; robot contacts use layer 16. The continuous visible wheel
has separate convex collision arcs, leaving its hand opening usable.

`runtime/cockpit_control.gd.set_physical_mode(true)` disables user handle drives;
passive spring centering and selector detents remain. A robot can then act through
contact. In MuJoCo, `source/cockpit_mujoco.py` supplies the same finite-force joints
and a command/event output API. A caller must dispatch that command bus to its
vehicle controllers; the isolated bench test is **not** a full MuJoCo cockpit-driving
integration or trained SaiRobot arm policy. Reach, grasp reliability, dual-arm
clearance, emergency operation and training remain unverified.

## Measured checks

- `check_cockpit_geometry.py`: continuous watertight 96-section wheel rim, maximum
  chord sagitta 0.126 mm; zero solid intersection between both front instrument
  panels and their console bodies; five distinct trim palettes.
- `check_cockpit_mujoco.py`: all 18 real joint/collider definitions tested on a fixed
  parent bench with finite actuators; .5 kg free contact probe physically presses
  WORK in passive mode. This is a mechanics/interface test, not a learned task.
- `check_cockpit_native.py`: 195 s Godot all-control scenario; ten physical button
  threshold events, third crane/third lift selected, four crane axes plus receiver
  axes moved, high range and park/stop exercised, all six lifts deployed/retracted.
- Near-field captures and five-theme review are generated by
  `review_cockpit_closeup.py`. Artistic approval requires visual inspection; no
  numeric test establishes parity with Microsoft Flight Simulator.
- `source/launch.py --mode ui_test`: runtime signal route. The 25 s r033 check
  selected crane 6 and lift 4, drove all four crane axes, both receiver axes and
  the three driving axes, changed camera/theme, and physically accepted WORK,
  LIFT, DOORS and PARK button presses. `operation_ui.json` records 26 UI events;
  `cockpit_controls.json` records the resulting measured joint positions.
- Interactive `manual` and `ui_test` modes use a 100 Hz physics loop with at most
  12 catch-up steps per rendered frame. Qualification scenarios remain at 200 Hz.
  Before this split, the complete vehicle's 6–8 ms physics tick exceeded the 5 ms
  budget and caused a catch-up spiral at 8–15 FPS. Three post-fix rendered UI runs
  measured 118.9, 123.7 and 121.4 median FPS; the manual run measured 122.0 FPS.
  `source/check_ui_fps.py` now fails below 30 median FPS.
